# QuickNotes data model

QuickNotes uses four core entities:

- **users** represent accounts that own notes.
- **notes** store a user's title and optional body.
- **tags** are reusable labels owned by a user.
- **note_tags** is the join table that associates notes with tags.

## Entities and columns

### `users`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `UUID` | Primary key, generated by the database |
| `email` | `VARCHAR(320)` | Required, unique |
| `password_hash` | `VARCHAR(255)` | Required |
| `display_name` | `VARCHAR(100)` | Required |
| `created_at` | `TIMESTAMPTZ` | Required, defaults to current time |
| `updated_at` | `TIMESTAMPTZ` | Required, defaults to current time |

### `notes`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `UUID` | Primary key, generated by the database |
| `user_id` | `UUID` | Required foreign key to `users.id` |
| `title` | `VARCHAR(100)` | Required |
| `body` | `TEXT` | Optional |
| `created_at` | `TIMESTAMPTZ` | Required, defaults to current time |
| `updated_at` | `TIMESTAMPTZ` | Required, defaults to current time |

### `tags`

| Column | Type | Constraints |
| --- | --- | --- |
| `id` | `UUID` | Primary key, generated by the database |
| `user_id` | `UUID` | Required foreign key to `users.id` |
| `name` | `VARCHAR(50)` | Required |
| `created_at` | `TIMESTAMPTZ` | Required, defaults to current time |

Each user can use the same tag name only once, enforced by a composite unique
constraint on `(user_id, name)`.

### `note_tags`

| Column | Type | Constraints |
| --- | --- | --- |
| `note_id` | `UUID` | Foreign key to `notes.id` |
| `tag_id` | `UUID` | Foreign key to `tags.id` |
| `created_at` | `TIMESTAMPTZ` | Required, defaults to current time |

The composite primary key `(note_id, tag_id)` prevents the same tag from being
attached to a note more than once.

## Relationships

- A **user has many notes** and each note belongs to exactly one user
  (`users` to `notes`, one-to-many).
- A **user has many tags** and each tag belongs to exactly one user
  (`users` to `tags`, one-to-many).
- A **note can have many tags**, and a **tag can label many notes**
  (`notes` to `tags`, many-to-many through `note_tags`).
- Deleting a user cascades to their notes and tags. Deleting a note or tag
  cascades to its rows in `note_tags`; the join rows cannot become orphaned.

## PostgreSQL table definitions

The application uses PostgreSQL. UUIDs are generated with `gen_random_uuid()`,
provided by the `pgcrypto` extension.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(320) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    display_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE notes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(100) NOT NULL,
    body TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE tags (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT tags_user_name_unique UNIQUE (user_id, name)
);

CREATE TABLE note_tags (
    note_id UUID NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
    tag_id UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (note_id, tag_id)
);
```

The foreign key from `note_tags` to `tags` does not by itself guarantee that a
tag and note belong to the same user. The service verifies that ownership rule
in the transaction that creates an association.

## Indexes

```sql
CREATE INDEX notes_user_updated_idx
    ON notes (user_id, updated_at DESC);

CREATE INDEX note_tags_tag_idx
    ON note_tags (tag_id, note_id);
```

`notes_user_updated_idx` makes the common "list this user's notes, newest
first" query efficient and supports pagination without scanning other users'
notes. The primary key already indexes `(note_id, tag_id)`, while
`note_tags_tag_idx` supports the reverse lookup of all notes using a tag.
PostgreSQL also creates indexes for the unique constraints on `users.email` and
`tags(user_id, name)`.

## Example queries

### List a user's notes

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE user_id = $1
ORDER BY updated_at DESC
LIMIT $2 OFFSET $3;
```

### Find notes with a tag (JOIN)

```sql
SELECT n.id, n.title, n.body
FROM notes AS n
JOIN note_tags AS nt ON nt.note_id = n.id
JOIN tags AS t ON t.id = nt.tag_id
WHERE n.user_id = $1
  AND t.name = $2
ORDER BY n.updated_at DESC;
```

### Create a note

```sql
INSERT INTO notes (user_id, title, body)
VALUES ($1, $2, $3)
RETURNING id, user_id, title, body, created_at, updated_at;
```

### Attach a tag to a note

```sql
INSERT INTO note_tags (note_id, tag_id)
SELECT n.id, t.id
FROM notes AS n
JOIN tags AS t ON t.id = $2 AND t.user_id = n.user_id
WHERE n.id = $1
ON CONFLICT (note_id, tag_id) DO NOTHING;
```

## SQL versus NoSQL decision

We chose a relational SQL database, PostgreSQL, because notes, users, tags, and
their ownership rules have clear relationships and require transactions. Foreign
keys, unique constraints, joins, and indexes enforce data integrity at the
database layer while supporting the API's list, search, and tagging queries.
NoSQL could scale flexible documents easily, but it would duplicate tag and
ownership data and move relationship consistency into application code. A cache
can handle high-volume reads later without giving up PostgreSQL as the source
of truth.
